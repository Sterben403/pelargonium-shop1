# Релизный план Pelargonium Shop

## Что считается релизом

Релиз — это **каждое слияние pull request в `main`**. После слияния GitHub Actions автоматически:

1. повторяет все проверки;
2. публикует Docker-образ сервера в GitHub Packages (`ghcr.io/sterben403/pelargonium-shop1:<коммит>`);
3. создаёт GitHub Release `v1.0.N` со списком изменений;
4. записывает GitHub Deployment в окружение `production` со статусом success или failure.

Мы выпускаем часто и маленькими частями: **одна задача — одна ветка — один PR**, ветка живёт не дольше дня.
Изменения не копятся до «большого релиза», поэтому при сбое сразу понятно, какое изменение виновато,
и его легко отменить.

## Окно релиза

| Когда | Правило |
| --- | --- |
| Понедельник — четверг, 10:00–18:00 (Астана) | обычное окно: сливаем PR, когда оба участника на связи |
| Пятница | только до 15:00, чтобы было время на откат до выходных |
| Выходные, праздники, отсутствие ревьюера | не сливаем |
| Исправление сбоя | в любое время — откат или исправление важнее окна |
| Заморозка | за 1 рабочий день до приёмки (M3, 20.12.2026) сливаем только исправления |

## Ответственные

| Роль | Кто | Что делает |
| --- | --- | --- |
| Автор PR | тот, кто делал задачу (Мурзаканов Еснур или Мурат Аяулым) | маленький PR с описанием и способом проверки; после выката 30 минут следит за сервисом |
| Ревьюер | второй участник команды | читает изменения, проверяет зелёный CI, ставит Approve |
| Ответственный за релиз | Мурат Аяулым | следит за окном релиза, принимает решение об откате |
| Владелец бизнеса | заказчик | принимает изменения, которые видят покупатели (каталог, заказ, тексты) |

Свои PR сам автор не сливает без одобрения второго участника.

## Чек-лист релиза

| Проверка | Как проверяется | Кто |
| --- | --- | --- |
| Изменение связано с задачей | ссылка на задачу в описании PR | автор |
| Оформление Markdown, тесты репозитория | CI: Docs and repository checks | автоматически |
| Стиль кода, 22 теста бэкенда на PostgreSQL | CI: Backend lint and tests | автоматически |
| Нет секретов в истории и уязвимых зависимостей | CI: gitleaks, Trivy | автоматически |
| Образ собирается, без уязвимостей HIGH/CRITICAL, работает как в продакшене | CI: Build and verify image — запуск, проверка версии, живой тест на 33 проверки | автоматически |
| Ревью пройдено | Approve второго участника | ревьюер |
| Видимые покупателю изменения согласованы | демо-страница из артефакта CI или локально | владелец бизнеса |
| Копия базы перед изменением схемы данных | `pg_dump` (см. ниже) | автор |

Если хоть одна автоматическая проверка красная, кнопку Merge не нажимаем.

## План отката

**Критерии отката — заранее и в цифрах:**

- `/api/health` возвращает не `200` или `"database": "unavailable"`;
- заказ не оформляется: живой тест (`backend/scripts/smoke_test.py`) не проходит;
- больше одной жалобы покупателей на каталог или форму заказа за час после выката;
- сканер нашёл уязвимость уровня CRITICAL в выпущенной версии.

**Порядок:**

1. Ответственный за релиз объявляет откат — без обсуждения «а может, само пройдёт».
2. **Основной путь — отменить изменение:** в слитом PR нажать **Revert** → GitHub создаёт PR с отменой
   → CI → слияние. Откат тоже становится релизом и попадает в историю Deployments.
3. **Быстрый путь, если CI недоступен:** запустить предыдущий образ — у каждого релиза есть свой тег:

   ```bash
   docker pull ghcr.io/sterben403/pelargonium-shop1:<коммит предыдущего релиза>
   ```

4. **Данные:** схема меняется только обратно совместимо (новые поля, без удаления старых).
   Перед изменением схемы делается копия базы:

   ```bash
   docker exec pelargonium-db pg_dump -U pelargonium pelargonium > backup.sql
   ```

5. Проверить каталог, оформление заказа и кабинет владелицы, сообщить заказчику результат.
6. Провести разбор без поиска виноватых и завести задачи по его итогам.

## Метрики

Метрики DORA считаются автоматически после каждого релиза по записям GitHub Deployments
(`scripts/dora_dashboard.py`): частота выпусков, lead time от первого коммита PR до выпуска,
доля неудачных выпусков и время восстановления. Дашборд прикладывается к каждому запуску
пайплайна в `main` (артефакт `dora-dashboard`), сводка видна на странице запуска.
